# 개선 아이디어 (codex + Sonnet 통합)

표기: n_i = 클라이언트 샘플 수, m_i = 서버 dev MSE, W_i = 로컬 가중치, W_g = 직전 global.
출처: C = codex, S = Sonnet. 둘 다 제안하면 신뢰도가 높은 방향입니다.

## A. 가중치 식 자체를 바꾸는 것 (구현 쉬움, global_aggregator.py만)

### 1. 통합 가중 스윕 — 출처 C·S ★최우선
- 식: w_i ∝ n_i^β · (m_i / median(m))^(−p), 정규화.
- (β=0, p=1)이 현행 MSEAvg, (β=1, p=0)이 FedAvg. 스윕 예: β∈{0,0.5,1}, p∈{0,1,2,4,8}. codex 변형은 (m_i+ε)^(−β)와 (n_i/Σn)^γ.
- 이유: 현행이 균등평균에 가깝다면 p로 신호를 키우고, n_i를 버리는 문제는 β로 복원. √n(β=0.5)은 크기 13배 불균형에서 중간값.
- 위험: p가 크면 한 클라이언트로 붕괴. 직렬 체인 편향을 오히려 증폭할 수 있음.
- 검증: FedAvg, 현행 MSEAvg와 같은 seed·같은 선택 시퀀스로 짝지어 비교.

### 2. 가중치 상한(clipping) — 출처 C
- 식: a_i = min(1/(m_i+ε), Q_p) 또는 a_i ≤ c/K 후 재정규화.
- 이유: 극단적으로 낮은 MSE 하나가 집계를 지배하는 것을 방지.
- 위험: 기준(p, c)에 민감. 진짜 우수한 클라이언트를 과소 반영.
- 검증: 가중치 최대값과 분포를 함께 기록. 아이디어 1의 p 스윕과 겹치므로 후순위.

## B. dev 점수의 신뢰도를 높이는 것

### 3. 서버 dev 표준화 정합성 확인/수정 — 출처 C·S
- 서버 dev를 클라이언트 scaler와 맞추거나, 점수 계산 방식을 바꿔 스케일 불일치의 영향을 확인.
- 이유: 점수가 틀리면 어떤 가중식도 의미가 줄어듦. codex는 이를 선결 조건 1순위로 꼽음.
- 위험: 의도(전역 일반화 측정)와 달라질 수 있음. 정합성을 맞추는 쪽이 항상 좋다는 보장 없음.
- 검증: 현행 방식과 정합 방식을 같은 조건에서 비교.

### 4. 클라이언트(소스)별 정규화 평가 + 공정성 가중 — 출처 C·S
- 식: dev를 클라이언트 블록 g별로 나눠 L_{i,g} 계산. z_{i,g} = L_{i,g}/L_{ref,g}, s_i = mean_g z (+ λ·max_g z), w_i ∝ n_i^β · exp(−s_i/T). codex는 macro-MSE 평균.
- 이유: 전체 평균 MSE는 재구성이 쉬운 소스가 지배. 평가가 10개 클라이언트 AUC 평균이므로 취지에 부합 (q-FFL류).
- 위험: 블록이 작아 추정이 노이즈. 비참가 소스의 분모 불안정(clip 필요). `main.py`에 블록 경계 전달이 필요(소폭 수정).
- 검증: 클라이언트별 AUC의 최저값과 분산도 함께 보고.

### 5. dev 부트스트랩 안정도 반영 — 출처 C
- 식: a_i ∝ 1/(m̄_i + λ·s_i + ε)^β, s_i = 부트스트랩 표준오차.
- 이유: dev 일부에서만 우연히 좋은 모델보다 일관된 모델 선호. 위험: dev가 작으면 표준오차도 불안정.

### 6. 잠재공간(Centroid) 정렬 가중 — 출처 S (hybrid 전용)
- 식: dev 정상의 잠재 z로 응집도 s_i = mean‖z_i(x) − c_i‖ 계산, w_i ∝ exp(−s_i/(T·std(s))). 또는 shrink loss 전체(MSE+λ‖z‖) 사용.
- 이유: 탐지가 잠재 Centroid 기반이라 AUC와 더 직접 연결.
- 위험: 잠재 노름이 작아지는 쪽으로 붕괴(정규화 필요). 클라이언트 간 잠재 좌표계 정렬이 보장되지 않음. AE(비-hybrid)에는 적용 불가.

## C. 집계 구조를 바꾸는 것

### 7. Greedy soup / dev shrink loss 직접 최소화 — 출처 S
- 식: dev loss 오름차순으로 클라이언트를 정렬해 하나씩 추가, 평균 모델의 dev loss가 줄어들 때만 포함. 변형: 단체 위 w를 소수 스텝으로 최적화.
- 이유: early stop이 보는 지표와 집계 목적이 일치하고, 해로운 클라이언트를 자동 제외.
- 위험: 작은 고정 dev에 과적합. dev loss가 내려가도 AUC는 안 오를 수 있음. dev를 선택용/보고용으로 분할해 확인 필요.

### 8. 서버 모멘텀 / EMA — 출처 S (C의 "global 모델 포함"과 유사)
- 식: Δ = Σ w_i (W_i − W_g), v = μv + Δ, W_g ← W_g + ηv. 또는 W_g ← (1−a)W_g + aΣw_i W_i.
- codex 변형: 직전 global을 후보로 포함하고 비중 ρ로 섞음 (ρ∈{0, 0.1, 0.25}).
- 이유: 50% 랜덤 참가의 조합 잡음과 비-IID 드리프트를 평활화. std≈1의 주원인이 조합 잡음이면 직접 효과.
- 위험: 오래된 방향으로 과이동. early stopping(patience=1)과 상호작용. 체인 학습 때문에 prev_global 저장 시점이 라운드 시작이어야 해서 `main.py` 한 줄이 필요할 수 있음.

### 9. 직전 global 대비 개선 가중 + 악화 클라이언트 거부 — 출처 S (C의 업데이트 크기 제한과 유사)
- 식: d_i = (L_i − L_g)/L_g, d_i ≤ δ만 남겨 w_i ∝ n_i^β · exp(−d_i/T). codex 변형: Δ_i = W_i − W_g를 ‖Δ_i‖ ≤ τ로 클리핑.
- 이유: 절대 MSE는 모델 간 비율이 평평하지만 "global 대비 개선"은 신호가 큼. 글로벌 손실이 단조 하락하면 조기 종료도 덜 걸림.
- 위험: 초기 라운드에 전원 탈락, 소수만 남아 다양성 상실. 직렬 체인이면 기준 L_g가 직전 클라이언트 모델이 됨.

### 10. Trimmed mean — 출처 S (후순위)
- 좌표별 상하 k개 제거 후 MSE 가중 평균. 참가 5명이면 3개만 남아 정보 손실이 큼. 이득이 낮아 후순위.
